# v1.0.0 iPhone 実機受け入れテスト

本番(cookdoor.app)にしかない状態(既存の v0.0.0 の Service Worker、家族のログイン状態と実データ)で
確かめる手順。ローカルと Preview で確認済みの項目も、実機で確認するまでは「合格」にしない。

## 前提と実施タイミング

- 実施者: 家族のうち1人(主担当)と、もう1人(家族共有の確認用)。iPhone を2台使えると良い。
- 本番デプロイの前に、`scripts/backup-and-verify.sh` でバックアップと復元検証が「合格」になっていること。
- デプロイは家族が料理や買い物の記録をしない時間帯(例: 夕食の片付けの後)に行い、デプロイ直後に
  この手順を続けて実施する。所要時間は約30分。
- 開始前に、主担当の端末で次をメモする(後で比較するため。スクリーンショットで可)。
  - 冷蔵庫の食材の件数と、任意の3品目の数量
  - レシピの件数
  - グループ画面の招待リンク
- 本番の DB には書き込まない。数量ボタンの確認は「＋を1回押して−を1回押す」の往復だけにする。

## 判定の書き方

各項目に「合格」「不合格」「未実施」のどれかを書く。未実施の項目がある間は、受け入れ完了としない。

## 1. v0.0.0 から v1.0.0 への更新

v0.0.0 の端末には「更新する」ボタンがない。新しい Service Worker は待機状態で止まり、
アプリを完全に閉じて開き直したときに切り替わる(docs/pwa-update-regression-checklist.md 参照)。

1. デプロイ後、ホーム画面のアプリを開いたまま1分待つ。
2. アプリスイッチャーで上にスワイプして、アプリを完全に終了する。
3. ホーム画面から開き直す。
4. グループ画面の一番下に「バージョン 1.0.0」が出ていれば合格。出ない場合は 2〜3 をもう一度行う。
   2回やっても変わらなければ不合格として、8 に進む。

## 2. バックグラウンド復帰時の更新確認

v1.0.0 になった端末で、次の版が来たときに検知できるかを見る。次の版(v1.0.1)を出すときに実施する。
v1.0.0 単独のリリースでは「未実施(v1.0.1 で確認)」と書く。

1. v1.0.1 のデプロイ前に、アプリを開いてからホーム画面に戻る(終了はしない)。
2. デプロイ完了後、アプリに戻る。
3. 数秒以内に「新しいバージョンがあります」が出れば合格。

## 3. 「更新する」で新しい版に移る

2 と同じく v1.0.1 のときに実施する。

1. 2 で出たダイアログの「更新する」を押す。
2. 画面が再読み込みされ、グループ画面のバージョンが新しい番号になっていれば合格。
3. ダイアログが出たまま消えない、または再読み込み後も古い番号なら不合格。

## 4. ログイン状態の維持

1. 1 の後、ログイン画面が出ずに冷蔵庫の画面が開けば合格。
2. ログイン画面が出た場合は不合格とし、メールのリンクでログインし直してから 5 を続ける。
   (ホーム画面のアプリはメールのリンクを Safari で開くため、ログインが引き継がれないことがある。
   この場合は Safari でログインした後、ホーム画面のアイコンを削除して追加し直す)

## 5. 冷蔵庫・レシピ・家族共有データの維持

1. 開始前のメモと比べて、食材の件数、3品目の数量、レシピの件数が同じなら合格。
2. もう1台の端末でも同じ食材が見えることを確かめる。
3. 主担当の端末で、ある食材の「＋」を1回押す。もう1台に数秒以内に反映されることを確かめる。
4. 「−」を1回押して元の数量に戻し、もう1台でも戻ったことを確かめる。

## 6. Safe Area の表示

v1.0.0 は画面のレイアウトを変えていない。ここでの結果は v1.0.1 で直す範囲を決めるために記録する。

1. 冷蔵庫の画面で、上端のグループ名と右上のボタンが時計や電波表示と重ならないこと。
2. 下端のタブ(冷蔵庫・レシピ・グループ)がホームインジケーター(画面下の横線)と重ならず、押せること。
3. 横向きにしても文字や操作が切れないこと。
4. 重なりがあれば、スクリーンショットを付けて不合格と書く。v0.0.0 と同じ状態ならリリースは止めず、
   v1.0.1 で修正する。

## 7. 入力中は更新が妨げにならない

本番では「更新が来るタイミング」を作れないため、次の版を出すときに合わせて行う。

1. v1.0.1 のデプロイ前に、レシピの「追加」画面でタイトルを途中まで入力したままにする。
2. デプロイ後にアプリに戻る。画面下に「入力が終わったら更新できます」の帯が出て、入力を続けられれば合格。
3. 入力を中断して一覧に戻ると、更新のダイアログに切り替わること。
4. 調理の確定ダイアログを開いたままでも、同じように帯だけが出ること。

## 8. 更新に失敗したときの復旧

**ロールバックする条件**(どれか1つでも当てはまれば、受け入れを止めて戻す)

- ログインし直しても冷蔵庫やレシピが表示されない
- 画面が真っ白のまま、または更新ダイアログが何度も出続ける
- 数量の「＋」「−」がエラーになる、または数値がおかしくなる
- 家族の端末のどちらかで、データが減っているように見える

**端末側の復旧**(本番の状態は変えない)

1. アプリを完全に終了して開き直す。
2. 直らなければ、Safari で cookdoor.app を開いて再読み込みする。
3. それでも直らなければ、ホーム画面のアイコンを削除し、Safari から「ホーム画面に追加」し直してログインする。

**本番の戻し方**(実施前に必ず承認を得る)

1. Vercel の Deployments で、直前の本番デプロイ(88f53b5)を「Instant Rollback」で戻す。
   保持期間の設定(本番デプロイは30日)により古い本番デプロイが削除されている場合は、
   main で v1.0.0 のコミットを revert して再デプロイする。
2. v1.0.0 では本番 DB を変更していないので、DB の復元は不要。データに異常が見える場合は、
   まず Supabase の SQL Editor で読み取り専用の件数確認を行い、バックアップの件数と比べる。
3. 戻した後、端末は上の「端末側の復旧」の 1〜3 で古い版に戻る。
