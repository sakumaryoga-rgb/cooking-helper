# v1.1.0 計画: エラー収集と利用状況の計測

BASKETBALL STATS(migration 031、`useErrorTracking`、`usePageViewTracking`、`sanitizeErrorText`)を
参考にする。**本番DBへのマイグレーション適用が必要なため、適用前にユーザーの承認を得る。**
DB を変更するリリースなので、`docs/db-backup-restore.md` のバックアップと復元確認を行う。

## 目的

- 家族の端末で起きたエラーに、報告を待たずに気づく。
- どの画面がどれくらい使われているかを、件数だけで把握する。

## 記録する内容(個人情報を残さない)

| テーブル | 列 | 書く人 | 読む人 |
| --- | --- | --- | --- |
| `client_errors` | created_at、user_id、app_version、path、message(500字まで)、stack(2000字まで) | ログイン中の本人 | 運営者のみ(service_role、または SQL Editor) |
| `page_views` | created_at、user_id、group_id、app_version、path(正規化済み) | ログイン中の本人 | 運営者のみ |

- 追記専用。update と delete のポリシーを作らない。
- `user_id = auth.uid()` を必須にし、`group_id` は `my_group_id()` と一致する場合だけ許す。
- path は `/recipes/:id` のように正規化し、クエリ文字列を含めない。
- message と stack は、送る前にクエリ文字列、JWT、Bearer、招待コードを伏せる。DB 側にも長さの制約を付ける。
- 食材名、レシピ名、メールアドレス、入力内容は送らない。
- BASKETBALL STATS と違い `app_version` を持つ。更新後に旧版のエラーが残っているかを見分けるため。

## 画面側

- `window` の `error` と `unhandledrejection` を拾う。React の描画エラーはエラー境界で拾い、
  「問題が発生しました。再読み込みしてください」の画面を出す(現在は真っ白になる)。
- Preview とローカルでは送らない(`DB_ENABLED` が false のときは何もしない)。
- 送信に失敗しても画面には何も出さない。同じエラーの連続送信は1分に1回までにする。
- 未ログイン時(ログイン画面)のエラーは送れない。必要になったら別途検討する。

## 確認方法

- DB テストに、他人の user_id や他グループの group_id では書けないこと、読めないこと、
  長さの制約が効くことを追加する(合成データのみ)。
- 単体テストで、伏せ字処理、パスの正規化、送信の間引きを確認する。
- Preview では送信されないことを確認する。

## 決定事項(2026-10-08)

1. 保存期間は90日。pg_cron で毎日自動削除し、使えない場合は手動の SQL で削除する。
2. 家族への説明は、グループ画面に1行表示する(`src/lib/telemetry/notice.js`)。
3. 集計は当面 SQL Editor で行う(`supabase/queries/usage_reports.sql`)。管理ダッシュボードは作らない。
4. 認証はメールリンクのまま。

実装の詳細は `docs/telemetry.md`、収集項目は `docs/privacy-data-inventory.md`。
