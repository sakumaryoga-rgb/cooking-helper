# v1.12.0 リリース手順(家の管理)

本番 SQL Editor で実行するのは `supabase/migrations/022_house_management.sql` だけ。**022 を適用してから v1.12.0 をデプロイする**。
011 と 017 は適用しない。022 は何度実行しても同じ結果になる。

## 既存データへの影響

- 削除・初期化はない。group_members に `role`(既定 member)と `display_name`(空)の列を追加する。
- 既存の家ごとに1行だけ `role = 'owner'` に更新する: 最初に参加した人(joined_at が最も古い人、同時なら user_id 順)。
  groups に作成者の記録はないが、create_group は作った人を最初のメンバーとして登録するので、通常は作った人になる。
  招待で入った家族が管理者になることはない(その家を作った人より後に参加しているため)。
  違う人を管理者にしたい場合は、管理者になった人がアプリで「管理者にする」で譲れる。
- 冷蔵庫・在庫・レシピ・調理記録・招待は変わらない。在庫やレシピの編集は、これまでどおりメンバー全員ができる。

## 適用からデプロイまでの間

v1.11.2 のアプリはそのまま使える(新しい列を読まない。家の作成・招待参加ではトリガーが role を自動で付ける)。
新しい関数は v1.12.0 からしか呼ばれない。古いアプリに更新を強制する必要はない(`minSupportedVersion` は 1.11.0 のまま)。

## 権限

| 操作 | 管理者 | メンバー |
| --- | --- | --- |
| 冷蔵庫・在庫・レシピ・調理・招待リンクの発行 | できる | できる(従来どおり) |
| 自分の呼び名(家ごと、20文字まで) | できる | できる |
| この家から脱退 | 先に管理者を譲る(ほかに誰もいなければ家を削除) | できる |
| 家の名前の変更・メンバーの退出・管理者を譲る・家の削除 | できる | できない |

権限はすべて DB の関数(security definer、search_path 固定、authenticated のみ)が、引数の家について auth.uid() の所属と役割を確かめる。
選択中の家のヘッダーには依存しない。group_members と groups には書き込みのポリシーがなく、関数以外からは役割を書き換えられない。
管理者は家ごとにちょうど1人(部分一意索引)。譲渡は同じトランザクションで「自分を member → 相手を owner」に替える。
アカウント削除などで管理者の行が消えた場合は、残っている最初のメンバーが管理者になる(トリガー)。

## 退出・脱退・古い招待リンク

- 退出させた人・脱退した人は、メンバーの行が消えた時点で RLS により、その家の読み書き・リアルタイム配信ができなくなる。
  古いブラウザや PWA から書き込んでも拒否される(DB テストで確認)。アプリは画面に戻ったときに所属を読み直し、その家の画面を閉じる。
- 管理者が退出させると、その家の有効な招待リンクを無効にする(古いリンクで戻れない)。必要なら発行し直す。
- 自分で脱退した場合は招待リンクを無効にしない(有効なリンクがあれば戻れる)。

## 家の削除

物理削除。groups の行を消し、外部キーの on delete cascade で、その家の食材・在庫ロット・レシピ・材料・調理記録・招待・
家庭専用の食材マスタ・別名・代替・使わない代替・メンバーを同じトランザクションで消す。利用状況・エラー・お問い合わせの記録は
group_id が空になるだけで残る。他の家の行は消えない(DB テストで確認)。アカウントは消えない。
確認として家の名前の入力を求め、DB でも名前の一致を確かめる。

### 論理削除(復元期間)を見送った理由

採用するなら: groups に deleted_at を追加し、is_group_member・my_group_id・全 RLS・招待参加で削除済みを除外、
復元の RPC と画面、期限後に物理削除する pg_cron、問い合わせ時の復元手順が必要。RLS の変更範囲が広く、
「削除したのに見える」などの不具合の危険が増えるため、家族利用の現段階では、名前の入力による確認と管理者限定で十分と判断した。
誤削除の報告が出たら、30日の復元期間つきで追加する。

## 切り戻し
